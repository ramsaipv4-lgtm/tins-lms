# b6-2: Pairing, devices, attendance

**SPEC rows:** AC-65, AC-66   **Model:** claude-sonnet-5-5   **Commits:** 8970f8bb537d9814580216136512c2c5c0fdf66a

## Decision
**Problem:** Pair devices with one-time codes, revoke them, and record attendance from a rotating code with a printed fallback, using core for every decision.
**Options considered:** (1) store pairing state in memory; (2) store the pure core PairingState in the private database as hashed codes and serialise claims; (3) a shared class password.
**Choice:** Option 2. Class attendance secret is random per class in the private database; printed code is an 8-digit hash per class day; rotating code is 6 digits from core.
**Why:** Private database survives restart and never replicates; hashes keep leaked copies useless; serialising stops a double claim; distinct code lengths remove ambiguity.

## What a learner will trip on
- SPEC does not say which person a device session belongs to; I added an optional `personId` on `POST /api/pairing`, otherwise the session is a `device-<id>` learner.
- SPEC does not say which class day an attendance mark belongs to; I use the day matching the clock date, or an explicit `day`.
- Revoking removes sessions only; a cookie-less repeat claim of a spent code is `used`.

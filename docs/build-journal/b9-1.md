# b9-1: Performance budgets and 200-learner load test CLI

**SPEC rows:** AC-100, AC-103 (AC-102 handed to b11-1, see the second decision)   **Model:** claude-sonnet-5-5   **Commits:** b19ba9b0909dcd33299f320ac9b2de732ce69c60

## Decision
**Problem:** AC-103 needs a CLI that makes 200 simulated learners sign in, mark attendance, answer a live quiz and sync against a local hub, and reports pass/fail as a JSON last line. AC-100 and AC-102 need the web build to stay inside its time and size budgets.
**Options considered:** (1) a library such as autocannon (not allowed: no new dependency); (2) per-phase scripts with log reading; (3) one CLI on built-in `fetch` that times every request and reads the stored documents back. For the budgets: change `vite.config.ts` chunking, or leave it if the build is already within budget.
**Choice:** Option 3 in `packages/cli/src/{main,loadtest,stats}.ts`, loopback targets only. `vite.config.ts` left unchanged: the entry chunk is 58 KB gzipped (index 180 KB raw), precache 272 KiB raw, with feature screens as lazy chunks.
**Why:** The hub has no live-quiz route, so quiz answers are `live` attempts (`POST /api/classes/:id/attempts`). The class and its 200 enrolments are created through `/db/class-<key>/_bulk_docs` as an admin/trainer session because the suite passes only `--target`, and the seed fixtures cannot be created by this task. Lost writes are measured by listing stored documents, not by trusting 2xx answers.

## Decision 2: AC-102 is not claimed here
**Problem:** After main gained b7-9 (offline), `acceptance/perf/budgets.test.mjs` failed AC-102: `AC-102: app shell JavaScript is 377.1 KB on the wire in 6 files (budget < 300 KB)`. The shell now loads index (245 KB raw, 77 KB gzip) and pouchdb (137 KB raw, 44 KB gzip) at start-up, and the server's static handler (`packages/server/src/core/static.ts`) sends no compression, so the test sees raw bytes.
**Options considered:** (1) edit `packages/web/vite.config.ts` chunking: only moves bytes between files, the raw total stays above 300 KB; (2) lazy-load pouchdb or trim b7-9's code: outside my scope; (3) compress static responses in the server: outside my scope; (4) claim the row anyway: false.
**Choice:** do not claim AC-102 in this task; the coordinator moved it to b11-1 (static compression). `vite.config.ts` stays unchanged.
**Why:** the fix lives in server or feature code I may not edit, and the progress file may list only verified rows. Gzipped, the shell would be about 130 KB.

## What a learner will trip on
- A 2xx from the hub is not proof the document is stored; read it back.
- The gate is slow on a shared machine; do not run it in a short-timeout shell.
- Failed requests must stay in the timing sample as `Infinity`.

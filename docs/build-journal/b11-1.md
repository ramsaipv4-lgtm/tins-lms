# b11-1: Server hardening and integration

**SPEC rows:** AC-102, AC-116, AC-120, AC-122 (AC-94 attempted, not claimed)   **Model:** claude-sonnet-5-5   **Commits:** e47e1f069f4befedd67447740e6bf2f34660ac40

## Decision
**Problem:** Nine groups merged into one server and left five real integration defects (strict enrolment ids, an instructor-script regex that never matched, a guard prefix that disagreed with SPEC, no English OCR data, compression in the wrong place), plus two rows nobody had built (AC-116 MCP, AC-122 minor integrity log).
**Options considered:** (a) patch each symptom where it showed up (a second app for sign-in, per-route compression); (b) fix each cause in the one module that owns the rule (guard, static server, enrolment lookup) and delete the workarounds; (c) for MCP, either execute write tools after a flag or make them only describe a change.
**Choice:** (b), and for MCP write tools that only store a pending proposal; a person confirms through `/api/mcp/pending/:id/confirm`, which forwards to the normal grade route with the confirmer's own cookie.
**Why:** a workaround that survives its cause is the next group's bug (b6-8 mounted a second app because the guard said `/api/sign-in`; main.ts then needed a path switch). Putting compression in `static.ts` means every static file gets it, with `Vary`, instead of only `/assets/*` on one feature's router. D-31 says AI proposes and people decide, so a write tool must be unable to write.

## Defects found while merging (verification)
1. Enrolment lookup / class day (attendance.ts): `store.get(db, 'enrolment:<personId>')` misses seed ids like `enrolment:c1-l1`; `todayIndex` only looked at package `day:` docs so a scheduled day with no content was recorded as the previous day. Fix: find the enrolment by its `personId` field, and let the class schedule decide the day. Proof: new test in `packages/server/test/attendance.test.mjs` (seeds `journeys/base.json`, clock 2026-11-05, expects `dayIndex` 3); it fails against the old `src/` (checked with `git stash push packages/server/src`) and passes after. content.ts had the same strict lookup for learners reading a day; fixed the same way.
2. publishPackage regex (content.ts): `/(^|\/)day0*${d.index}\/instructor_script\.md$/` is a regex literal, so `${d.index}` is literal text and never matches. Sealed bodies held only titles. Fix: `new RegExp(...)`. Proof: new test in `content.test.mjs` opens a released section and asserts the body has more than one line; against the old code it printed `body is the script section, not the bare title: "Warm-up"`.
3. Guard prefix (guard.ts): `/api/sign-in` became `/api/signin`; `registerSignin` is now called from `accounts.ts` and the separate Hono app and path switch were removed from main.ts. Proof: `signin.test.mjs` (AC-62/AC-81) and `acceptance/api/roles.test.mjs` stay green; `hardening.test.mjs` asserts `isPublicApi('/api/sign-in/passkey') === false`.
4. English OCR data (coach.ts): `tessdataPath` now falls back to `@tesseract.js-data/eng/4.0.0_best_int/eng.traineddata.gz` (the small 2.9 MB file tesseract.js uses by default). Proof: `hardening.test.mjs` gunzips the served file. AC-94 itself is NOT claimed, see the mistakes table.
5. Compression (static.ts): the I-8 work had already put brotli/gzip in `static.ts`, so the brief's premise was out of date; the real defect was the second implementation in `board.ts` that answered `/assets/*` first. I moved its extras (immutable cache header, a best-effort warm-up that compresses the board chunk at brotli 11) into `static.ts`, deleted the middleware from board.ts and compressed the OCR core scripts too. Proof: `static.test.mjs`, `acceptance/perf/budgets.test.mjs` (AC-100, 101, 102 all `ok`).

## Open question: AC-94 desktop "1 !== 0"

In a failing run (E18 log, run captured while investigating) the server saw only the `coachMeta` PUT (PIN setup) and no `coachEntry` before the failure; the OCR requests came about 160 ms after that PUT. In passing runs the same sequence appears (coachMeta, then coachEntry only after Confirm). Hypothesis, unverified because acceptance sources are off limits: the journey counts the PIN's `coachMeta` document when its baseline is taken before PIN creation lands. Needs the journey owner to say what is counted.

## What a learner will trip on
- A regex literal is not a template: `${...}` inside `/.../` is just characters.
- A guard that disagrees with SPEC gets worked around by the next group; fix the source.
- "Read-only" is a property of the tool, and a write tool that cannot write is safer than one with a flag.
- A test that passes on the broken code proves nothing: stash the fix and watch it fail.

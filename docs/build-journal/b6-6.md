# b6-6: Export, import, signed class packages, device keys

**SPEC rows:** AC-74, AC-75, AC-76, AC-77   **Model:** claude-sonnet-5-5   **Commits:** adbf74e, final commit by kit close

## Decision
**Problem:** The hub must export everything as a verifiable tar, load such a tar into an empty server, sign class packages, accept learner files signed by device keys, and never leak a secret.
**Options considered:** (1) zip of JSON trusted by origin; (2) tar plus manifest plus ECDSA signed containers built from the core functions of SPEC 4.24; (3) one shared password for encryption.
**Choice:** Option 2 in `packages/server/src/routes/export.ts`. Hub key pair made on first use and stored only in the private database; device public keys also kept in the private database; data files `data/<db>.json` carry the lossless documents for import, CSV/MD/ledger/events/board files are views.
**Why:** signatures prove the author, manifests catch exact damage, and core already provides every primitive (D-22).

Other choices (SPEC is silent): section bodies are left out of class packages (AC-68); a signer must hold an active enrolment in the class (403 for unknown signer, 400 for bad signature or corrupt); secret-looking keys are removed from every exported and imported document; the personal databases are not part of the admin export (coach data stays with the learner), only `/api/me/export` includes the caller's own.

## What a learner will trip on
- The ledger's own `hash` field matches a "ends with hash" secret pattern; it must be kept or exported ledgers cannot be verified.
- Cache the key-generation promise, not the key, or two first requests make two keys; clear it on test reset.
- Section `body` in a package would bypass sealed release.

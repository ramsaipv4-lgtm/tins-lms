## Decision
**Problem:** Five journeys share one team and class context and need screens, server routes and exact accessible names. SPEC Appendix D for corporate and forge is cut off in the middle of a sentence.
**Options considered:** (1) one route file per journey; (2) one server module that resolves the caller's class from the session and keeps all documents in the class database; (3) client-side state with sync.
**Choice:** Option 2: routes in packages/server/src/routes/features/shift.ts, screens code-split per route in packages/web/src/features/shift/.
**Why:** The Shift needs one server clock; the rituals need shared state between learners; the class database already replicates documents.

## Orchestrator note: integration I-10 (AC-164 prod deploy on the phone profile)

AC-164 "a prod deploy needs an approved change request" [phone] failed in every full-suite gate and
passed alone. Trace evidence: the trainer's `POST …/decide` returned 200, and the learner page
re-fetched `/api/corp/change-requests` 48 times (all 200) for 40 s without "Deploy to prod" ever
reading as enabled. Cause: the button rendered *disabled* while the change requests were still
loading, so a check made right after navigation saw "not approved" whenever the fetch was slower than
the check (throttled phone, loaded machine). Fix: show a loading status instead of the button until
the data has arrived; the button's disabled state now always means "no approved change request".
The earlier `cache: 'no-store'` change (M15) was a plausible guess but not the cause.

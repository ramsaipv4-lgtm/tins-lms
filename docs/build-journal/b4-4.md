# b4-4: Conflict merge

**SPEC rows:** AC-28, AC-29   **Model:** claude-sonnet-5-5   **Commits:** 9047a570ed0755336df32b22e3e4a8a6b1c57c40

## Decision
**Problem:** Merge revisions of one document so the result is order-independent, idempotent and associative, with class-owned fields taken only from hub revisions.
**Options considered:** whole-document latest-wins plus array union; a merge whose result also records provenance (per-element rank, statuses seen, hubFields with their time).
**Choice:** the second. Winner = largest (updatedAt, updatedBy), content as last tiebreak. Result carries `hubFields` and `mergeMeta` (elements, statuses).
**Why:** a result is later merged as a revision. Without provenance an element, a ticket badge or a hub value from an earlier merge is judged by the result's rank and gives a different answer than merging the originals.

## What a learner will trip on
- Treating a merge result as a plain document: the badge and element winners are lost on re-merge.
- A carried `hubFields` entry must win over the revision's own field, or a stale value gets the later revision's time.
- Judgement call where SPEC is silent: with no `hub:` revision at all, the winner's value is kept for class fields. Equal (updatedAt, updatedBy) with different content is not guaranteed associative.

# b3-4: Manifests, tar archives, signed class packages

**SPEC rows:** AC-42, AC-43, AC-44   **Model:** claude-sonnet-5-5   **Commits:** 415c2eb

## Decision
**Problem:** Export a class as files that a receiver can check for completeness, integrity and origin, with no dependencies and no file-system access in core.
**Options considered:** (1) an npm tar/zip library; (2) hand-written POSIX ustar plus sorted SHA-256 manifest plus ECDSA P-256 signed container; (3) JSON with base64 bodies.
**Choice:** Option 2 in `packages/core/src/export.ts`.
**Why:** D-3 forbids new dependencies; ustar is small and can be checked by the system `tar -tf`; Web Crypto gives ECDSA. The container is `LMSP1\n`, key length, signer public key, 64-byte signature, archive. `openPackage` verifies the signature with the embedded key (`bad-signature`), then checks the trusted list (`untrusted`); malformed input or a bad tar is `corrupt`.

## What a learner will trip on
- The ustar checksum is summed with the checksum field as eight spaces; a round trip through your own code cannot reveal a wrong rule, only `tar -tf` can.
- Octal size fields are text with a NUL terminator, 11 digits plus NUL for 12 bytes.
- Names over 100 bytes need the prefix field, split at a `/`.
- A valid signature from an unknown key is `untrusted`, not `bad-signature`.

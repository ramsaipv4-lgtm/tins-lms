# b12-1: Last two rows: accommodation timer and screenshot OCR

**SPEC rows:** AC-153, AC-94   **Model:** claude-sonnet-5-5   **Commits:** 53ae25f0b92304507461ab3b34805baed308d562

## Decision
**Problem:** AC-153: an approved accommodation was stored (person.accommodations.timeMultiplier) but the Shift screen only rendered `shift-timer` while a shift was running, so a learner who opened Shift to look at their limit saw no timer. AC-94: the phone profile never reached `shot-confirm` in time, and the desktop profile failed about every other run with "no document may be saved before the learner confirms".
**Options considered:** AC-153: (a) start a shift automatically; (b) show the limit in the not-started state, computed by the server with the same `limitFor` the running shift uses. AC-94 speed: (a) a different data file; (b) start the worker when the screen opens, shrink the picture, stop unzipping in script. AC-94 desktop: (a) wait longer before the check; (b) make the first document of the personal database appear at a predictable moment.
**Choice:** AC-153 (b). AC-94: (b) for both, plus never dropping a file that is chosen before the screen is ready.
**Why:** starting a shift has side effects (a run is stored, tickets arrive); showing a number does not. The server owns the multiplier so the screen cannot disagree with the running shift. For OCR the log of timings showed the phone was bound by fetching 3 MB over the throttled link, so the lever is to start early, not to compute less; the flake was an ordering problem, not a slow one.

## What a learner will trip on
- A `disabled` input still gets files from automation, and the handler that ignores them looks like a slow OCR.
- A count taken "before" and "after" only means something if the thing being counted cannot change in between.
- Beacons (`navigator.sendBeacon`) are a quick way to see inside a throttled browser, but remove them before committing.

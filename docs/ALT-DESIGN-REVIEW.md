# Coach LMS, Plan v10: a contrarian second opinion

**Reviewer stance:** independent product architect. I read PLAN.md (v10, all 984 lines), SIMULATED-RUN.md (v3), FAILURE-QUESTIONS.md (46 rows) and the handwriting RESULTS.md. Claims I could not check here are marked *verify*. Licence notes come from memory and must be confirmed before any decision.

## 0. Summary

The plan is careful and honest. It verifies its facts, labels what it has not checked, and puts a fallback behind every dependency. The handwriting experiment is a model of how to settle a design question with evidence. The problem is scope against capacity. One person who teaches all day is specifying about 36 modules, more than 54 integrated resources, two AI tiers, a native app, a LAN server with its own certificate authority, a self-hosted forge, container labs and an HR/payroll suite. The whole thing is to be generated by Haiku and Sonnet on a release-candidate framework.

The simulated run had **one student**. Everything that will actually break is at 60 to 200 students: the network, proxy attendance, support load and lab capacity. The run never exercised that.

My main alternative is:

- **Build less.** Write only the parts that make this product different: the Shift, the package import plus content gate, the coaching framework and the teleprompter.
- **Borrow the rest:** the forge, chat, lab environments, the flashcard scheduler and the sync engine.
- **Start cloud-first with an offline cache,** not local-first with a hub.
- **Prove learning gains with real students in 4 weeks** before building the personal-OS half.

## 2. The smallest thing that delivers value in 4 weeks

**Goal:** one real batch of 30 to 60 students next month, with evidence that learning improved.

### What ships (built)

1. **A web app (PWA) on one cloud server** with join code, roster and login by phone OTP or Google.
2. **Package import + content gate (M-26)**, read-only. It renders `student_guide`, `deepdive` and `quicklearn` for each day. The gate is the most differentiated thing you already have, and it caught real drift in package5.
3. **Daily quiz + spaced cards.** The quicklearn diagnostic becomes a scored quiz. Missed items and `memory_recall` items become FSRS cards (ts-fsrs), with a "due today" list and nothing else.
4. **Teleprompter (M-33)** as a single page on your phone, rendering `instructor_script.md`. This is a one-week build and pays off every class.
5. **One Shift**, as a plain web page: a seeded ticket queue, SLA timers, and checks that run as scripts on a single cloud lab VM. Score at the end.
6. **Trainer grid:** students × days with quiz %, cards reviewed and Shift score, plus CSV export.

## 3. Architecture alternatives

### 3.1 Local-first + hub vs cloud-first with an offline cache

**What the plan does well.** P-1 respects the reality of weak campus Wi-Fi, and the event-log idea is sound in principle.

**The cost the plan underestimates.** Local-first with a LAN hub buys you:

- a private certificate authority on the laptop (F-11);
- hub discovery after IP changes (F-13);
- client isolation on campus Wi-Fi (F-12);
- clock trust for graded timers (F-17);
- schema versioning across offline devices (F-21);
- crypto-shredding against append-only logs (F-24);
- a stolen laptop holding the whole cohort's data (F-41);
- you as the single point of failure (F-01).

Ten of the 46 failure questions exist *because of* the hub topology.

**My alternative.**

- **Cloud-first.** One small VM or PocketBase instance in an Indian region (*verify* region availability and price) is the source of truth.
- **The PWA caches** content for the next 7 days, plus the card queue and quiz answers, in IndexedDB. It queues writes in an outbox.
- **Graded work** gets a server-signed start time and is submitted when back online. It is flagged if it was submitted late.
- **The "no internet at college" case** is handled by a **₹1,500–3,000 4G router or your phone's hotspot** (*assumption* on price). That is cheaper than months of LAN engineering.
- **Keep a LAN hub as phase 3**, only if real sites prove they have no mobile data at all.

**"Hub on every student laptop".** Cut it. Most students in your segment will have a low-end laptop, no laptop, or a deep-freeze lab PC (F-18). A personal hub doubles the support surface (Windows Defender, ports, firewall prompts) for marginal benefit. Put labs in the cloud and keep personal data on the phone.

### 3.2 Sync model

The plan describes "events with device id, append-only ledgers merge, profile latest-wins". That is event sourcing with LWW registers. It is correct but **easy to get subtly wrong**: ordering, idempotency, schema upcasting and tombstones.

If you keep local-first, use a library rather than letting Haiku write it:

- **CouchDB/PouchDB** for document replication;
- **Automerge or Yjs** for the board and notes (CRDTs, MIT);
- **ElectricSQL/PowerSync** for Postgres→SQLite partial sync (*verify* licences).

### 3.3 A single SQLite file per learner

This is attractive for P-5 and deletion. One encrypted file per learner makes crypto-shredding and export trivial, and restore is "copy a file". Cloudflare Durable Objects and Turso's per-tenant databases follow this pattern (*verify*). For a solo operator, **per-learner SQLite for the Coach space + one shared DB for class data** is a clean split that matches P-5 exactly.

### 3.4 PWA vs native (Capacitor)

**Phase 1 should be a PWA:**

- It works on iPhones too (F-14), with caveats on iOS storage eviction (*verify*).
- No Play Store review.
- No Data-safety form while there are no finance/health trackers.

**Go native only for features that need it:**

- reliable local notifications (Android OEM battery killers, F-16);
- camera QR (a PWA can do this via `getUserMedia`);
- on-device models.

Capacitor around the same Svelte app is a reasonable step 2.

### 3.5 The stack for AI-built code

**Effect v4 RC.** Models will write Effect v3 or pre-Effect TypeScript. Your own plan notes the API renames. A pinned RC plus a crib sheet means every Haiku task fights its training data. Effect's value (typed errors, schemas, retries) can be had more cheaply:

- **Zod or Valibot** for schemas;
- a `Result` type (neverthrow, or 20 lines of your own);
- **Hono** or **Fastify** for the server.

Models write Express/Fastify/Hono and Zod very reliably.

**Svelte 5 vs React.**

- Svelte 5 runes are recent. Models frequently emit Svelte 4 syntax (`export let`, `$:`). It is fixable with a lint gate, but it is a constant tax.
- **React + Vite** is the most-written frontend in training data, and Excalidraw *is* React. Choosing React removes the "only React island" split.
- The bundle-size argument for Svelte is real but modest. React 19 + Vite with code-splitting on 2021-era phones is fine for a content app (*verify* with a Lighthouse run on a target device).

**My stack for weak-model builds:**

- TypeScript, Node 22, **Hono** (server) and **Zod** (schemas);
- **React + Vite PWA**;
- **SQLite via better-sqlite3 or PocketBase**;
- **Vitest** + Playwright;
- ts-fsrs.

The plan is right about plain-TS zero-dependency pure functions for the core. That is the best decision in §4.2.

**`node:sqlite`.** It is experimental in Node 22. Fine for tests, but pin it, or use better-sqlite3 in production (*verify* its status in Node 24).

### 3.6 HTTPS on a LAN

If the LAN hub survives, the cleanest route is a **real domain with DNS-01 certificates**. You obtain certificates for `hub.yourdomain` once, while online, and resolve that name to the LAN IP (through a local DNS override or by publishing the private IP in DNS). That avoids per-device CA installs. This trick is used by Plex-style products (*verify* renewal and expiry constraints, and that the browser accepts private-IP A records). It is still more moving parts than cloud-first.

## 4. Pedagogy first

### What is well grounded

- **Retrieval practice:** memory_recall, quicklearn diagnostic and closed-book exercises (Roediger & Karpicke 2006).
- **Spacing:** the Anki/card system (Cepeda et al. 2006 meta-analysis).
- **Commit-before-reveal / predict-then-reveal:** generation effect and prediction.
- **Faulty-first content:** this links to error-based learning and "productive failure" (Kapur). The evidence is supportive but conditional: the error must be explained and the correct model then consolidated, which your diagnosis → fix sequence does.
- **The Shift:** authentic, timed, auto-checked practice gives fast feedback on transfer tasks. This is the most original pedagogical idea in the plan.
- **Trace tables:** worked examples plus self-explanation for program comprehension.

### What is missing or underweighted

| Practice | Gap | Suggestion |
|---|---|---|
| **Mastery learning** (Bloom; Kulik et al. meta-analyses) | There is a skill map but no mastery gate. Students advance by calendar day | A per-skill mastery threshold (e.g. 80% on two spaced checks). Non-mastered skills get remediation cards and a re-check. Show "not yet" rather than a fail |
| **Feedback latency** | Postmortems are scored by Laya plus trainer confirmation, which may take days | Instant automated feedback on checks. Trainer feedback within 24 h as a tracked SLA for *you* |
| **Worked examples → faded examples** (Sweller; Renkl) | Live coding is replayed, but there is no fading | Each lab step goes from full example, to partially completed, to blank (completion problems) |
| **Interleaving** | Cards are per day; the Shift interleaves, but study doesn't | Mix card decks across days after week 1. Add mixed-topic quizzes |
| **Delayed retention measurement** | The placement retest happens at the course end, which overstates retention | A retest 3–4 weeks after the course |
| **Elaborative interrogation / self-explanation** | Feynman cards exist | Make "explain why" a required field in Shift postmortems and the predict step |
| **Peer instruction** (Mazur) | Live quiz only | Vote → discuss in pairs → re-vote. It's cheap with an existing quiz tool |
| **Cognitive load** in a 6-hour day | 7 artifacts + 3 companions + board + lab + Shift per day | A daily *minimum path* (what to do if you only have 40 minutes) |

### What a learning scientist would cut or downweight

- **Story mode (manhua).** Risk of the *seductive details* effect. Presentation-only gamification has mixed evidence. Keep it off by default.
- **Leaderboards and contribution walls.** These motivate the top quartile and can demotivate the bottom. Use personal-best and team-level displays instead.
- **The hour-by-hour life plan, money, food and relationship quests.** These may help some adults, through implementation intentions (Gollwitzer). But they are not linked to learning outcomes in a bootcamp, and they triple privacy obligations (F-36, F-38). Treat them as a separate product decision, not a bootcamp feature.
- **Git commit-count metrics.** Easily gamed. Use them for diagnosis only, never for grading.
- **Elective integrations** (RAISE, ROSBLOCKS, Sucre4Stem…). Link out instead.

## 5. Business and operations

*Assumptions are marked (A).*

### What Indian colleges actually ask for

- **Attendance in their format.** Many institutions enforce a minimum, often 75% (A, *verify* per university).
- **A completion report** per student.
- **NAAC/NBA-style CO-PO attainment** evidence. Your curriculum skill already mentions CO-PO tracking, so make it an export.
- **Placement outcomes**, or at least "certifications earned".
- **Invoices with GST.**
- **Data staying with the college** (F-46).

Personal-life coaching is not on that list (A). A coordinator buys attendance + outcomes + a credible certificate.

### Solo support load

At 60 to 200 first-time users, your bottleneck is installs, passwords and permission prompts, not features (F-45). Every extra moving part multiplies support: native app, hub, pairing, personal hub, Forgejo account, container runtime. Cloud-first PWA plus Google/OTP login plus cloud labs is the lowest-support design.

**Budget an hour of support per 20 students in week 1 (A),** and measure it.

## 6. AI-built-software risk

### Most likely to be built wrong

| Rank | Part | Why weak models will fail it |
|---|---|---|
| 1 | **Sync engine** (event merge, LWW, offline queue, schema versions) | Distributed-systems correctness. The tests pass on the happy path and the system fails in the field |
| 2 | **Effect v4 hub code** | Training-data mismatch (v3 APIs) |
| 3 | **Modified Excalidraw** (pages, sidebar, stroke isolation for handwriting) | A large React codebase with internal APIs, and frequent upstream changes |
| 4 | **Crypto** (passphrase backup, per-user keys, crypto-shredding, LAN CA) | Subtle and security-critical. Models misuse IVs, KDF parameters and key storage |
| 5 | **Capability check + fallback matrix** (about 15 rows × switching) | Combinatorial. Each fallback is a second implementation to keep alive |
| 6 | **Shift timers and grading** under clock skew | Fairness bugs |
| 7 | **Payroll / GST invoices** | Domain law the model does not know |
| 8 | **Svelte 5 runes UI** | Syntax drift |
| 9 | **Package import mapping** | Messy real files. Lower risk, because you have a real fixture (package5) |
| 10 | **Scheduler** | Low risk if you use ts-fsrs. High if SM-2 is written from scratch |

### How I'd restructure SPEC and tasks for weak models

1. **One task = one pure module ≤ 300 lines with a frozen interface file** (`*.d.ts` or a Zod schema) written by Sonnet or you *before* Haiku starts. Haiku implements behind the interface; it never designs one.
2. **Golden tests from real fixtures.** package5 is gold: import it, snapshot the mapped output, and review the snapshot once. Do the same for the syllabus XLSX → topic list. Use seeded Shift runs → exact score JSON.
3. **Property tests** for the ledger (sum invariants), scheduler (intervals monotone on "good"), seeded RNG (same seed, same paper) and merge (commutative, idempotent). Properties catch what example tests miss in model-written code.
4. **Reference implementations as patterns.** For the 5 "proven" components the plan expects (SM-2/FSRS, money ledger, seeded RNG, question parser, event log), keep a hand-checked reference in tins-kit. The task becomes "adapt the reference", not "invent".
5. **Dependency budget:** at most 8 runtime dependencies for the app, each a locked D-row. Prefer libraries with large training-data presence.
6. **Vertical slices over layers.** "Day page shows quiz → answer saved → card created → due tomorrow" end to end, with a Playwright test. Weak models do better finishing small vertical slices than integrating layers built by separate tasks.
7. **Hidden acceptance suite:** keep it, but also give builders a *visible* smoke subset so they can self-check. Otherwise Haiku iterates blind.
8. **Separate "integration adapters" from core** with a contract-test kit. Every adapter (GitHub, Forgejo, R2, Drive) must pass the same contract test against a fake. Write only one real adapter per capability in phase 1.
9. **Sonnet for anything with state across time** (sync, timers, crypto). Haiku for pure functions and CRUD screens.

## 7. Things the plan is missing entirely

1. **A measurement plan for learning outcomes.** There is no control comparison, no delayed retest and no definition of "it worked". (§4 partially adds the delayed retest.)
2. **The student acquisition / enrolment funnel:** how students get the app, a login method that works without email (many Indian students use phone numbers), and password reset without you.
3. **Authentication specifics:** OTP/Google login, session handling and account recovery. F-20, F-23 and F-35 circle this, but there is no auth design.
4. **Reporting in the college's format:** attendance sheets, CO-PO mapping export, per-semester summaries, PDF reports on letterhead.
5. **Observability for a solo operator:** error tracking (e.g. Sentry free tier, *verify*), uptime alerts, a daily digest (F-44 asks for it, but there is no module).
6. **Release management:** staging, feature flags in production, rollback (F-43). P-14 switches are product switches, not deploy safety.
7. **Accessibility** beyond F-09: WCAG targets, screen-reader testing, low-literacy UI.
8. **Low-bandwidth content delivery:** asset sizes, image compression, and video avoidance on 2G/3G fallback.
9. **Content QA beyond form.** F-27 is right that the gate checks format, not truth. The plan needs SME review sign-off and a learner "report error" loop as modules, not afterthoughts.
10. **Academic integrity in an AI-everywhere world** beyond the graded-window AI lock (F-08). It needs assessment design that is AI-resilient: oral defence of the capstone, live Shift explanation, and viva questions generated from the student's own repo.
11. **Trainer scale-out.** If this works, you will hire trainers. That means content handover, trainer onboarding to the tool, and quality comparison across trainers.
12. **Exit plan / data portability** for colleges: export everything as CSV/Markdown, so the first procurement objection has an answer.
13. **A cost dashboard:** cloud spend, lab hours and AI token spend per batch.
14. **A decision on whether "Coach (personal OS)" and "Academy (bootcamp)" are the same product.** Part I says one app. I'd argue the evidence for coupling them is thin, and the coupling triples privacy and legal scope.

## (b) The 10 changes I'd make first, ranked

1. **Run a 4-week Wizard-of-Oz pilot** with one real batch on the minimal slice (§2), with pre/post and delayed retests defined in advance.
2. **Switch to cloud-first PWA with an offline cache.** Shelve the LAN hub and personal hubs.
3. **Move labs to one cloud VM** (code-server/JupyterHub) with per-student namespaces and server-side checks.
4. **Replace Effect v4 + Svelte with Hono + Zod + React** (or at minimum drop Effect). Lock at most 8 dependencies.
5. **Adopt PocketBase (or another existing sync/auth backend)** instead of writing sync, auth and file storage.
6. **Use ts-fsrs** and add per-skill mastery gates with remediation.
7. **Split the personal-life Coach out of the college product.** Keep only the learning-plan part of the coaching framework.
8. **Make GitHub the primary forge** (Classroom + App bots), with Forgejo as the offline sidegrade.
9. **Restructure SPEC into frozen interfaces + golden tests from package5 + property tests**, with vertical-slice tasks. Sonnet handles stateful parts and Haiku handles pure parts.
10. **Write the college-facing outputs first:** attendance with a rotating code, completion report, CO-PO export and a privacy notice/DPA template (F-37, *lawyer verify*).

## (c) Five things I'd keep exactly as planned

1. **The Shift (M-10):** seeded, timed, auto-checked enterprise tickets with blameless postmortems. This is the product's genuine differentiator and is pedagogically sound.
2. **Package import + content gate (M-26, P-9):** "one validated format, one validator that fails loudly". It already proved its worth by catching the COURSE-MAP drift in package5.
3. **P-2 "AI proposes, people decide" and P-3 "works with no AI"**, including scripted AI teammates as the deterministic default. They are cheap, gradeable and robust.
4. **P-6/P-7 deterministic seeds and pinned graded work, plus P-10 append-only ledgers for grades.** Fairness and auditability are exactly what colleges will question.
5. **The teleprompter on the trainer's phone (M-33) and the coaching framework's low-friction mode (accept defaults, ≤ 25 taps).** One is small and saves you effort every class. The other is the right UX principle and carries a measurable acceptance target.

Also keep the practice behind the **handwriting experiment**: settle each risky design question with a small, scored experiment on real material before writing the SPEC row. Apply the same discipline to the sync, lab and network questions above before committing to the local-first architecture.
